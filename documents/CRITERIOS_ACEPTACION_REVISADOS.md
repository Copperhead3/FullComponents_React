**Fuente:** `Plantilla_Gestion_Requerimientos_Scrum_Epicas_PC.xlsx`, hoja «Historias de Usuario» del frontend HTML entregado.

Este inventario conserva la numeración y los criterios originales. **No equivale a una certificación de cumplimiento**: el frontend puede implementar una interfaz, pero las transacciones y reglas de negocio requieren pruebas con el backend real y con MySQL.

Leyenda:
- **Implementación frontend presente; E2E pendiente:** existe una pantalla o lógica para la historia; falta verificar todos los criterios con el backend.
- **Parcial:** una parte de la historia está implementada, no todos sus criterios.
- **Pendiente/no verificado:** no hay evidencia suficiente en el frontend y los controladores entregados para certificar la historia.

## Limitaciones confirmadas en los controladores incluidos

1. `Usuarios/ClienteController` solo tiene POST, GET y PUT. No existe DELETE de clientes ni API para crear administradores desde React. La pantalla permite **editar** clientes, no borrarlos.
2. El Gateway permite el acceso directo a las rutas de mantenimiento de Producto y Clientes. El panel React comprueba el rol, pero **eso no sustituye la autorización en el backend**. No se puede declarar satisfecho el criterio de seguridad/roles hasta implementar Spring Security o controles equivalentes.
3. El backend no expone un controlador de promociones y cupones; la sección visual de ofertas muestra productos seleccionados y **precios reales**, sin inventar descuentos.
4. El módulo de compatibilidad de componentes, reseñas, devoluciones y notificaciones no está acreditado con los servicios recibidos.
5. Las integraciones MySQL, pagos, despacho y compra necesitan pruebas de punta a punta con los siete microservicios funcionando; **no se han ejecutado en este entorno**.
6. Algunas funcionalidades del HTML original eran solo visuales o dependían del localStorage. La versión React orienta catálogo, stock, usuarios y pedidos al Gateway cuando `VITE_USE_MOCK=false`.
7. `ServiceProducto` responde texto simple en POST/PUT; el adaptador React maneja ese contrato sin asumir que recibe el producto JSON. La creación de producto localiza su nuevo ID mediante un listado posterior.
8. La actualización de clientes exige un objeto `Cliente` válido, incluso un campo `contrasena` que su método de servicio no utiliza. Se envía un valor de relleno de validación **sin alterar la contraseña guardada**; lo correcto a futuro es un DTO de actualización sin contraseña.
